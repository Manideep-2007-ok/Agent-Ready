# AgentReady: Decision log

Each decision: what we chose, why, and what we rejected. Change a decision only with the team; add a new row or mark the old one "Replaced by Dxx".

| # | Decision | Why | Rejected alternatives |
|---|---|---|---|
| D1 | **JavaScript (ES modules) + JSX**, no TypeScript | The team knows MERN; under deadline pressure, errors must be easy to read and fix. Shared shapes still exist as JSDoc in `types.js`, which editors and agents read | TypeScript: safer types but build steps and type errors cost time today |
| D2 | **Express + React (Vite) + Node 20**, npm workspaces monorepo | MERN skills; one repo, one `npm install`; engine shared by server, CLI and CI | Next.js (new to the team), separate repos (sync pain) |
| D3 | **No MongoDB yet: JSON files behind `store.js`** | Zero setup, doubles as the demo cache, one module to swap for MongoDB later | MongoDB Atlas: ~15 min setup and one more thing that can fail on stage |
| D4 | **Call TinyFish with plain `fetch`** | Exactly what we tested on 31 Oct; no SDK version surprises | TinyFish SDK: fine, but untested by us |
| D5 | **All TinyFish calls only in `packages/engine/src/tinyfish.js`** | One place to fix bugs, add mock mode, and respect limits | Calls scattered across apps |
| D6 | **API key only on server and CLI** (`.env`); screenshots proxied via `/api/shot` | Keys must never reach the browser; step screenshot URLs need the key | Exposing screenshot URLs directly (they need a TinyFish login anyway) |
| D7 | **Server -> dashboard via SSE** | One-way live updates are all we need; simplest to build and debug | WebSockets (two-way, more code), polling (laggy lanes) |
| D8 | **Scoring is plain code; AI only writes fix explanations** | Reliable, explainable, cheap, same result every time | AI-judged scores (vary per run, hard to defend to site owners) |
| D9 | **`TINYFISH_MAX_PARALLEL` setting (default 2) with a queue** | TinyFish connector says this account allows 2 concurrent; on 31 Oct 3 started and a 4th waited ~70 s | Firing everything at once (runs queue silently and lanes look frozen) |
| D10 | **Time cap on every run** (`max_duration_seconds`, default 150) | Keeps cost and demo time bounded; tested that the agent reports just after the cap | No cap (big stores took up to 261 s) |
| D11 | **SSE stream drop -> poll `GET /v1/runs/{id}` every 3 s** | Tested 31 Oct: stream dropped (curl error 56) but the run kept going and finished | Treating a drop as failure |
| D12 | **Bot-wall cascade: no proxy -> India proxy -> stealth** | A large store tested on 31 Oct blocked the no-proxy run and passed with the India proxy alone; stealth only if still blocked | Always stealth (hides the real finding and costs more) |
| D13 | **Only trust agent claims backed by steps** | A shopping agent named a store it never visited; one run gave a wrong answer on example.com | Taking agent JSON at face value |
| D14 | **Demo store: static site on Vercel with switchable flaws** | TinyFish's cloud browsers cannot reach a laptop; small sites run in ~30 s; before/after is guaranteed | Fixing a real site (impossible), localhost demo (needs a tunnel on stage) |
| D15 | **Watch with node-cron + async runs + webhook (polling fallback); alert only after 2 failures** | Webhook tested OK; agents vary so one failure is not enough | TinyFish Monitor (watches content changes, not agent tasks) |
| D16 | **Alerts via Discord/Slack incoming webhook** | One POST, no SDK, nothing to set up | Email (setup, spam folders) |
| D17 | **Detailed Fix Report instead of copy-paste code fixes** | Real sites use many frameworks; a generic snippet would often be wrong. We give evidence, cause, standard, framework-aware example, pass check | "Code fix generator" (only works for our demo store) |
| D18 | **Fix write-ups: one AI call per finding, JSON output, template fallback** | Makes the report read well; never blocks the demo if the AI call fails | No AI (flatter text), AI-only (fragile) |
| D19 | **Localhost CLI via Cloudflare quick tunnel** | Tested 31 Oct from Manideep's laptop: no account, no warning page, agent passed in 28 s | ngrok/localtunnel (show a "click to continue" page that blocks agents) |
| D20 | **Mock mode (`TINYFISH_MOCK=1`) replaying real 31 Oct runs** | Three people can build UI all day without spending credits | Building against live runs (costly, slow) |
| D21 | **Feature flags for every Tier 2+ feature** | Hide a broken feature during the demo without touching others | Removing code under pressure |
| D22 | **Never word a finding as "the agent got confused"; always a site cause** | Findings must help the site owner act, and must not read as a failure of the agent platform | Neutral agent logs only |
| D23 | **Race Mode uses 3 sites, not 4** | Parallel-run limit (D9) | 4 lanes with one stuck "waiting" |
| D24 | **Dropped from the first build (1 Nov):** AI Shopper Panel, Monitor-based watcher, Research brief, auto-competitors (Search), Datasets leaderboard, badge, locked previews, Vault logins, Agent's-eye view, separate Visitor Matrix | Untested, slow, or weak on stage; kept for the roadmap slide | |
| D25 | **Instant Scan findings live in `SiteReport.scanFindings`; shown in the findings list; can enter Top 3 but rank after point-scoring findings of the same severity** (Top 3 order: severity, then `pointsIfFixed`, one per finding type) | A pop-up covering the page is a real blocker even though it costs no points; without its own field it could only appear in Top 3. One bot-wall fix covers every task it blocked, so the same fix never fills all three slots. Agreed by Manideep (and for Akhil) on 1 Nov | Option B: scan findings only inside Top 3 (no contract change, but they vanish from the findings list) |
| D26 | **Bot-wall cascade stops after the India-proxy attempt if it failed after 5+ steps; verdict `none` (site failure, not a bot wall)** | Watch demo 1 Nov: a broken cart said "Something went wrong", which matched the block pattern, so the engine ran proxy + stealth (₹111 instead of ₹10) and reported "agents could not use this site" with an allow-list fix. An agent that moved around the site from a home address got past any wall. The store whose wall we saw on 31 Oct is unaffected (passes on attempt 2). Agreed by Manideep 1 Nov | Narrowing the block-words pattern (a real bot wall seen on 31 Oct also says "Something went wrong"); always running stealth (cost, wrong label) |
| D27 | **Replaced by D44.** **Dashboard uses a few Magic UI components (theme toggler, smooth cursor, line-shadow text, globe, bento grid, icon cloud, confetti, comic text) via Tailwind v4 without its reset** | Team asked for a more polished demo look on 1 Nov. Components live as `.tsx` in `apps/web/src/components/ui` (Vite compiles them; app code stays JS). Tailwind loads theme + utilities only, the app's CSS sits in the components layer, so nothing else changes. Globe is lazy-loaded; cursor/confetti are off with reduced motion or touch | Full TypeScript/shadcn rebuild (too big for the day), no new UI libraries (plainer look) |
| D28 | **Answer checks: `wrong-quantity` (medium) and `currency-mismatch` (low) are findings only, built from the agent's own answer or step labels; they never fail a task or change points** (ARCHITECTURE section 7) | 2 Nov: an agent "passed" add-to-cart after adding 2 units (reported ₹998) and another reported "$499" for a ₹ price. The engine cannot know the truth, but the agent's own words can show a likely problem. A guess must not cost a site owner points, so these are findings with "may" wording and a site cause (a quantity box starting above 1, a hidden second currency). Conservative patterns only ("quantity: 2", "2 units", "x3"; a dollar price with no rupee sign while the site shows rupees) | Failing the task on a suspicion (unfair, hard to defend); AI-judging the answer (D8); re-running the task to compare (cost) |
| D29 | **`CANCELLED` is final; a real cancel flow** (engine `cancelReport` / `cancelAll`, `POST /api/tests/:id/cancel`, Stop test button, CLI Ctrl+C, Watch pause). A cancelled run is never "blocked": no bot-wall retry, nothing queued for that test starts, in-flight runs are cancelled on TinyFish. A cancelled report has status `cancelled`, score 0, no findings, and keeps its cost | 2 Nov: a cancelled run has few steps, matched the "blocked" rule, and the cascade started new proxy/stealth runs (money) while queued tasks kept starting | Treating cancel as a failed task (still retries); only aborting our stream (the run keeps spending on TinyFish) |
| D30 | **Queue priority: a person's test (web, CLI, race) goes ahead of waiting Watch checks; running runs are not pre-empted. Queue state is public in `GET /api/health`, and lanes say why they wait** | 2 Nov: a scheduled Watch check held both slots and the Test page sat on "Waiting for an agent" for minutes with no explanation | Pre-empting a running Watch task (wastes the steps already paid for); a separate pool for Watch (only 2 agents on the account) |
| D31 | **Every endpoint validates its input; start-a-test endpoints are rate limited (10/min per client and endpoint, `429`); foreign-origin POSTs are refused (`403`); Watch is 5-1440 minutes and at most 20 watches; at most 6 tests run at once** | Each test spends agent steps, and a body-less POST (cancel, run-now) can be sent by any web page open in the browser even though CORS hides the answer. A 1-minute Watch would cost about ₹3,000 a day per task | Trusting the dashboard to send good input; relying on CORS alone |
| D32 | **Server robustness: it loads `.env` itself (a missing file is fine), recovers reports left `running` by a restart (they become `cancelled`), cancels in-flight runs on SIGINT/SIGTERM, ignores unreadable report files, answers EADDRINUSE with a clear message, and writes one JSON log line per test/watch event** | `npm start` crashed without a `.env` (`--env-file`); a restart left lanes spinning forever; a failed port bind was swallowed by the crash guard and left a server that did not listen | Keeping `node --env-file` (needs the file, Node 20.6+ flags differ); only the crash guard |
| D33 | **Dependencies: vite 7 and node-cron 4** (`npm audit` clean). The dashboard build needs Node 20.19+ (vite 7) | vite 5/6 pulled an esbuild with a dev-server advisory; node-cron 3 pulled a uuid with a bounds-check advisory. node-cron 4 keeps `schedule()`/`stop()`, which is all we use; the build and the Tailwind plugin work unchanged | Staying on vite 5 and documenting the dev-only advisory |
| D34 | **Tests: `node:test` (no framework) for engine, server and CLI; an in-process fake TinyFish (`packages/engine/test/fake-tinyfish.js`) for failures the recordings do not have; Playwright click tests in `apps/web/e2e`** | The owner wants every behaviour proven by running it. The fake replaces `fetch`, refuses any other host and uses a dummy key, so tests cannot reach or bill the real API; everything else runs with `TINYFISH_MOCK=1` | A test framework (more setup); calling the real API (credits) |
| D35 | **Replay mode never shows an unrelated answer for a custom task: the lane carries `replayNote` ("Replay: this answer is from a recorded run, not your custom task") and no answer; recorded-site matching uses exact domains, not substrings** | A custom task replayed a recording of another store and looked like a real result; a look-alike domain (`evil-<store>.com`) matched that store's recording | Hiding the custom task in replay mode (the box would look broken) |
| D36 | **Race and Leaderboard are back in the dashboard (hidden on 1 Nov, shown for the public launch); each tab appears only when the server flag is on (`/api/health` `features`)** | Public launch (2 Nov): both pages already had working APIs and recorded data, and the demo-day cut (D24 era) no longer applies. Race stays at 3 sites (D23). The winner is the passed site with the fewest steps, then the fastest, and is named only when every site has finished. A stopped race names no winner (D29). In replay mode a race refuses sites with no recording, like a test does (D35) | Leaving them hidden; showing the tabs unconditionally (a flag turned off for a demo would leave a dead tab) |
| D37 | **CI check is a reusable composite action (`action.yml` at the repo root), and our own workflow runs only on PRs labelled `agentready` (plus manual runs); it tests the Vercel preview of the commit, else the production demo store; without the secret it skips green; one PR comment edited in place (hidden marker `<!-- agentready -->`)** | Every run spends real agent steps (about $0.016 each), so it must be opt-in per PR. A root `action.yml` gives the shortest `uses:` line for the LinkedIn launch. Editing one comment avoids a pile of comments on every push. Cancel-in-progress per PR plus a signal trap makes the CLI cancel TinyFish runs when a job is cancelled. Markdown is built by a tested script (`scripts/ci-report.mjs`), not inline shell | Running on every PR (cost); a `.github/actions/` composite (longer `uses:` path); a new comment per run; Docker or JavaScript action (build step, more to maintain) |
| D38 | **`@agentready/cli` is published from a generated folder (`scripts/pack-cli.mjs` -> `dist/cli`): CLI plus a copy of the engine source with two import paths rewritten; `playwright-core` is the only dependency; `apps/cli` stays `private`** | The engine is a private workspace package, so `npm publish` on `apps/cli` would ship a package nobody can install. Plain file copying needs no bundler (ask-first rule) and keeps one source of truth; the same folder is what the Action installs, so CI tests what users get. Pack tests check the layout and run the packed CLI outside the repo | `bundleDependencies` with workspaces (symlink and lockfile surprises); publishing the engine as a second package (two versions to keep in step); a bundler such as esbuild (new dependency) |
| D39 | **The Agent-Ready badge is a pure engine function (`badgeSvg`), written by the CLI (`--badge`) and served for dashboard reports at `GET /api/badge/:id.svg` (5 minute cache, grey "unknown" badge for missing ids)** | A visible score on READMEs and posts is the cheapest growth loop. Pure and escaped, so it cannot inject markup; unknown ids never return an error image that breaks a README | A third-party badge service (shields.io needs a public endpoint); a PNG (needs an image library) |
| D40 | **Task packs: AgentReady tests any kind of site, not only shops. Four packs of four tasks (`shop`, `saas`, `content`, `local`); `SiteReport.pack` is a `PackId` (older `'shopping'` reads as `shop`); `TaskId`, `FindingType`, `Watch.pack` and two optional `InstantScan` fields (`schemaTypes`, `keywordHits`) are added to the contract. Shop ids, wording and order do not change. Pack auto-detect is a pure function of the Instant Scan (`detectPack`): highest keyword/schema score wins, shop only through product signals, no signal or a tie goes to content, then saas, local, shop. Price findings in the Instant Scan are shop-only. Answer checks (D28) stay shop-only. The new goal wording is untested on live agents until `docs/PACK-LIVE-TEST.md` is run** (approved by the owner 2 Nov) | AgentReady was a shopping tool in the pitch, but most sites are not shops: a SaaS site is judged on pricing and sign-up, a clinic on hours and booking. The scoring rules need no change (4 x 25, scaled for fewer), so a pack is only goals, labels, fail findings and fix templates. Detection from the scan the dashboard already runs costs nothing extra and is unit-tested with fixtures. Keeping the shop ids means old reports, fixtures, Watch and the 31 Oct recordings keep working. Replay mode has recordings only for the shop tasks, so a task from another pack is not run there (note, no points, no findings), like the custom task (D35) | One generic "find the key page" task (hides what is wrong); AI-chosen tasks per site (varies per run, D8); renaming the shop ids to `shop_*` (breaks every saved report and fixture); defaulting unknown sites to shop (it would flag a blog for "no price") |
| D41 | **Confirm results is opt-in: a second run with the same mode and proxy, a third only when the two disagree; the majority decides, a disagreement is a "flaky" task with an `inconsistent-results` finding (no points)** | Agents vary between runs (RESEARCH section 4: example.com right once, wrong once), so one run cannot carry a public score. Repeating every test triples the bill, so the person running the test chooses (dashboard toggle, CLI `--confirm`, API `confirm`); Watch already re-runs a failing task before alerting. Bot-wall `blocked` tasks are not repeated: the cascade already ran them up to three times | Always 3 runs (3x cost on every test); always 2 + tiebreak (2x cost by default); repeating the whole cascade (stealth runs again) |
| D42 | **Claim checks read the page the agent itself named (TinyFish Fetch, free) and look for the facts it reported (return days, price digits, email, phone); a mismatch or another website is an `unconfirmed-claim` finding (low, no points); an unreadable page stays unchecked** | D13 says trust only step-backed claims, but nothing checked them. Fetch costs nothing, and only the agent's own words are tested, so a page that draws its facts in images is the likely cause (a site cause, D22). Never a failed task: a page can show the fact only after a script runs | Failing the task on a mismatch (unfair to script-built pages); asking the agent for evidence in the goal (GOAL_SUFFIX must not change); AI-judging the answer (D8) |
| D43 | **Spending limits: a cost estimate before every test (`GET /api/estimate`), a per-test limit enforced live by the engine (`BUDGET_PER_TEST_RUPEES`, default ₹300; the test stops with `stopReason: 'budget'`), and an optional per-day limit on the server (`BUDGET_PER_DAY_RUPEES`, `429` when spent)** | Confirm runs and bot-wall cascades multiply cost; a hosted version needs a ceiling per test and per day before Watch or the India report scale up (build plan risk "Cost"). ₹300 covers a 4-task confirmed test on a large store (about ₹170) with room for one cascade | No limits (one bad site can burn the wallet); a limit on tasks instead of rupees (cost depends on steps, not tasks) |
| D44 | **One design system for app, landing, pricing and docs: paper-and-ink tokens with one ember accent (`#C2410C` light, `#FF7A3D` dark), Inter + JetBrains Mono self-hosted, 4 px corners, ledgers, a sidebar workbench for the app; plain JSX components in `apps/web/src/design`; Magic UI pieces, Tailwind and their dependencies removed; app moved under `#/app/...` with redirects for old links. Replaces D27** | Going from hackathon demo to product (build plan Phases 3 and 6): the confetti, comic burst, custom cursor and globe read as a demo. Direction agreed 7 Nov from Postman (a workbench for people who run tests) and Vouch (paper and ink, mono labels, evidence ledgers), with our own accent so it copies neither. One token file keeps colours identical everywhere and a test keeps them at WCAG AA. Removing the `.tsx` kit settles P1-4 (plain JS, D1) and halves the JS bundle (478 kB to 282 kB) | Keeping Magic UI and restyling around it (two systems, TypeScript files stay); shadcn + Tailwind rebuild (TypeScript, new dependencies); Vouch's teal and layout as is (would look like a copy of another TinyFish product) |
| D45 | **Structured answers: every agent run sends `output_schema` (`ANSWER_SCHEMA` in `goals.js`, the same four fields as `GOAL_SUFFIX`); `GOAL_SUFFIX` stays unchanged. If TinyFish refuses the field (HTTP 400 naming it), the run is sent again without it and later runs skip it** | The agent sometimes answered in prose or nested JSON, which the parser had to guess at (`parseAgentAnswer`). With the schema the result is the object itself (checked on a live run, 7 Nov: 4 steps, exact shape). Keeping the tested wording means nothing changes for accounts or recordings without it | Replacing the goal wording with the schema (untested wording, rule 8); failing the run when the field is refused (an account setting would break every test) |
| D46 | **TinyFish Search and Monitor (P2-5). Search: the Instant Scan searches the site's own domain for the two key pages of its pack; a miss is a low `not-in-search` finding (no points). Monitor: watches of 2 hours or more get an hourly Page Monitor whose relevant change starts the check early, at most once an hour** | Assistants often search before they visit; a returns page with a generic title is invisible to them even when agents can click to it (seen on a live store, 7 Nov). Search is free. A watch every few hours can miss a bad deploy for hours; a Page Monitor costs $0.005 a run and reads the page without an agent, so the paid agent check runs only when something changed. The hourly cap and the unguessable monitor id stop a forged webhook from running up agent costs | Searching every topic of every pack (slower, more noise); a Topic Monitor (watches the web, not the page); triggering on every change (cookie banners and dates change constantly); Monitor on short watches (the watch already runs often) |
